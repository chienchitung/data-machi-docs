企業團隊可把查試算表、讀專案狀態或執行操作包裝成工具（Tool）。模型會收到工具名稱、用途與輸入規格，由應用程式管理實際呼叫。

以 Data Machi 為例，`query_worksheet_data` 查詢並彙總試算表資料，`search_document_base` 從 PDF 查找相關內容，`get_project_status` 則取得專案看板狀態。模型不需要知道底層 API 怎麼寫，只需要知道什麼情況應該使用哪個工具，以及要傳入什麼資料。

## 函式呼叫（Function Calling）到底做了什麼？

模型可以依工具規格回傳工具名稱和參數。應用程式驗證這些參數與權限後執行函式，再把結果送回模型。有些 SDK 會代為處理這段往返。

例如詢問平均訂單金額時，模型可以判斷該查哪個來源，實際篩選、加總與除法則由 Pandas、SQL 或其他程式執行。詳見 [Gemini 函式呼叫文件](https://ai.google.dev/gemini-api/docs/function-calling)。

## 那 LangChain 又是什麼？

LangChain 提供共用介面，讓開發團隊能串接模型、提示詞（Prompt）、訊息、工具與輸出，並重用函式規格（Function Schema）、工具綁定（Tool Binding）與訊息交換的程式。

但 LangChain 並不是「裝上去就會自動變成代理（Agent）」。資料應該去哪裡查、欄位怎麼定義、什麼情況需要重新查詢，以及哪些動作需要人工確認，這些仍然是產品與工程設計問題。

## 不要把框架當成業務邏輯

框架最有價值的地方，是幫你少寫重複整合程式；最危險的地方，是讓人誤以為只要使用某個代理類別，系統就會自然懂公司的流程。

Data Machi 用框架處理模型與工具的接合。資料來源、欄位定義和核准條件由應用程式管理，團隊日後換模型時仍可沿用這些業務規則。

## 進階理解｜一個好工具，至少要說清楚四件事

對非工程背景的讀者，不需要先記 JSON 結構規格（JSON Schema）。只要把工具想成「交給 AI 使用的一項公司能力」，它至少要說清楚：**叫什麼、什麼時候用、需要哪些輸入、會回傳什麼。** 例如 `get_project_status` 如果只描述成「查資料」，協調者（Coordinator）很容易和其他工具混淆；如果明確寫成「當使用者詢問專案目前狀態、負責人與截止日時使用」，分流就會穩定很多。

| 工具要回答的問題 | 例子 |
| --- | --- |
| 名稱（Name）｜它叫什麼？ | `get_project_status` |
| 用途說明（Description）｜何時使用？ | 查詢專案目前進度與負責人 |
| 參數（Parameters）｜需要什麼？ | 專案名稱或 ID |
| 回傳結果（Return）｜會得到什麼？ | 狀態、負責人、截止日、來源 |

<Accordion title="延伸閱讀：LangChain 比較像轉接層（Middleware），不是 AI 大腦">
  LangChain 的價值主要是幫忙統一模型、訊息與工具的接法，降低不同 API 之間的整合成本。它不會替你決定公司的正確流程、資料定義與安全邊界。可以把它想成「轉接層」：讓不同零件比較容易接起來，但產品要解決什麼問題、哪些步驟不能出錯，仍然需要另外設計。
</Accordion>
